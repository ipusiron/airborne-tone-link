**Day120 - 生成AIで作るセキュリティツール200**

Airborne Tone Linkは、短い文字列をスピーカーからマイクへ渡し、その通信路をスペクトログラムで見る学習ツールです。
可聴・近超音波の両方で、文字がUTF-8のバイト、2本のトーン、受信文字列へ変わる過程を確かめられます。
暗号化はしていません。同じ方式を知る受信者は内容を復元できます。

## ✨ 主な機能

- 1バイトを上位・下位4ビットに分け、別々の16候補から2本のトーンを同時に出力
- 「可聴」と「本気（近超音波）」の周波数帯。音の長さ（85/192/384ms）と全文の回数（1/2回）は共通設定
- 送るだけ・受けるだけ・物理的な折り返し・WAVのオフライン復元
- 32本のデータトーンを拡大したスペクトログラムと、UTF-8文字単位のライブ復元
- CRC-8、確信度、折り返し時の文字一致率
- マイクの加工状態の表示、日英切り替え、明暗切り替え、キーボード対応

## 📖 使い方

### 2台で送受信する

先に冒頭の「機器名を確認」で、ブラウザーが開いたマイク入力と既定の出力先を確認します。「マイクをテスト」は5秒間の入力レベルを表示し、「スピーカーをテスト」は1kHz・0.4秒・−30dBFSの音を1回鳴らします。マイクテストは音を出さず、スピーカーテストはマイクを開きません。停止・ヘルプ・非表示・離脱でも終了します。

表示名はブラウザーの報告で、オーディオインターフェースの先につながるマイクやスピーカー本体を特定するものではありません。取得できない名前は未確認と表示します。入力レベルは音圧ではなく、テスト音が実際に聞こえたかどうかも自動判定しません。機器名や音声を保存・外部送信しません。

1. 両方の端末を開き、同じ周波数帯と音の長さを選びます。最初は「可聴」を使います。
2. 受信側は「受けるだけ」を選び、開始してマイクを許可します。
3. 送信側は「送るだけ」を選び、256バイト以内の短文を入力します。
4. OSの音量を小さくし、開始します。受信側の文字列とCRCを確認します。
5. 近超音波を試す場合は、両方を「本気」に変更します。

`HELLO`は5バイト、`日本語`は9バイト、`😀😀😀😀`は16バイトです。
出力レベルの横の小さな「?」で、数値を変えたときの音の大きさとOS音量との関係を確認できます。入力欄には全文の送信予定時間を表示します。256バイトでは既定設定で約103秒、「もっと長い・2回」で約205秒です。送受信中は画面を前面に保ってください。

既定は「可聴・長い192ms・全文2回」です。周波数帯を切り替えても音の長さと回数は変わりません。16kHz付近が聞こえる人もいます。
同時送信は避けてください。自動応答や再送要求はありません。方向を逆にする場合は役割を切り替えます。

### 1台で折り返す

「折り返し（1台）」はスピーカーからマイクへ実際に音を渡します。
1kHzの短い自己点検音が背景より10dB以上増えたことを確認してから、本送信を開始します。
ヘッドホンではマイクまで音が届かず、自己点検で止まる場合があります。
加工がオンなら確認ダイアログを表示します。表示は要求値ではなく、マイクが報告した実値です。

### WAVを復元する

「オフライン復元」を選び、このツールと同じフレーム形式のWAVを読み込みます。
PCM 16/24/32bit、float 32bit、8〜96kHz、1〜2チャンネル、128MiB以内、300秒（5分）以内に対応します。
ファイルのレートで選択帯域を解析できることが必要です。圧縮WAVとWAVE_FORMAT_EXTENSIBLEは対象外です。
ステレオは左右を平均するため、逆相の音は相殺されます。他方式の音声モデムや話し声は復元できません。

WAV復元はマイクも音声出力も使いません。選択したファイルは端末内だけで読み、終了・停止後に選択と解析用データを解放します。

### 復元した文字列と受信成功の違い

「音から復元した文字列」は、受けるだけ・折り返しではマイク入力、送るだけでは送信波形、オフラインではWAVから読み取った候補です。送る文字列をコピーして表示することはありません。読み取り中は未検証で、CRC・終了マーカー・UTF-8の検証結果を別に表示します。

本文を1バイトも読み取れていなければ「復元できた文字はありません」と表示します。「?」は読めなかった位置の目印で、取得した文字ではありません（元の文に含まれる「?」を除きます）。読み取れたバイト数と読めなかったバイト数を併記します。途中で停止した候補は未検証のまま残し、モード・役割の切り替え時に前回の結果を消去します。

グラフの横軸は12秒幅です。選んだ音の長さと回数に応じて右側に未計測の時間が残ります。同じ設定なら両帯域の送信時間は同じです。「未計測」は無音の測定結果や受信失敗を意味しません。フレームを最後まで読み取れなかった場合も、途中の候補がある場合と本文を読めなかった場合を分けて確認してください。

### 送った音と届いた音を比較する

文字を復元できなかった場合は「受信状況」を確認します。2トーンの判定、マーカーの種類、開始の合図、長さ情報、本文バイト、フレーム検証、解析の最大間隔を試行ごとに表示します。未到達の段階を検証成功と扱わず、別の送信回の本文バイトも合算しません。終了時も失敗した段階を残します。グラフに音が見えるだけでは、文字通信の成功にはなりません。

既定の「折り返し」では、上段にスピーカーへ渡した波形、下段にマイク入力を表示します。両方を別々の解析器で測定し、同じ時刻・周波数・色の尺度で描画します。受信側への直接接続はありません。上段は端末内の送信波形であり、スピーカーが実際に空気中へ出した音の測定ではありません。上下の差を校正済みの減衰量として扱わないでください。

周波数帯だけを切り替える比較では、音の長さ・回数・入力文字列・音量・機器の配置をそろえます。既定の長い音・2回なら、`HELLO`の送信波形はどちらも5.742秒です。受信の遅れも共通時間軸に現れます。

「送るだけ」では上段だけ、「受けるだけ」では下段だけを測定します。他端末の送信波形はその端末で確認してください。WAVは下段に表示します。受信・WAV復元では送信時と同じ音の長さを選びます。以前の可聴モードで作ったWAVは「長い192ms」で読み込めます。回数は送信側だけの設定で、「受けるだけ」は最初の正常なフレームで終了します。
録音や音声ダウンロードの機能はありません。

## 🎯 ユースケース

### このツールならではの使い方

| 問い | 操作と得られる例 |
|---|---|
| 文字数と通信量は同じか | `HELLO`は5文字・5バイト、`日本語`は3文字・9バイト。見かけの長さと通信時間の違いを確かめる |
| 同じ文字が続くと何が見えるか | `AAAA`では1,876Hzと3,098Hzの2本が続く。文字が変わらなくても同期時計で4バイトとして読む |
| どの周波数が欠けると読めないか | 2台で向きや距離を変え、スペクトログラムのA/B両ブロックを見る。片方だけでは4ビットが足りず「?」になる |
| 速さの数字は何を数えているか | 既定設定の256バイト送信は両帯域とも102.894秒・正味2.49B/s。付帯情報を除く2.60B/sとの違いを計算する |
| 通信と秘密は同じか | 公開短文を別の受信端末でも読む。CRCの成功は暗号化や送信者の認証を意味しない |

授業や展示では、可聴モードで仕組みを説明してから近超音波へ進めます。
音響条件を分けて確認したいときは、同じフレームのWAVを使うと部屋や機材の経路を含めず復元を確認できます。

## 🔬 通信方式と判定

| 項目 | 値 |
|---|---|
| 文字コード・上限 | UTF-8、256バイト |
| トーン | ブロックAが上位4ビット、ブロックBが下位4ビット、計32候補 |
| 周波数間隔 | 94Hz。48kHz・FFT 2048で約4ビン |
| データ帯の幅 | 2,914Hz（31間隔）。専用マーカーはF0−188HzとF0−94Hz |
| フレーム | 交互マーカー4、長さ1または3、本文0〜256、CRC1、終了マーカー2 |
| CRC | CRC-8/SMBUS：多項式0x07、初期値0、反転なし、最終XOR 0。長さと本文を対象 |
| FFT | 2048点、Blackman窓、平滑化0、候補の最寄りビン±1の最大パワー |
| 確信度 | 最大候補と2位のパワー比。各ブロック6dB以上で採用、低い側の値を表示 |
| 出力 | 計算した正弦波のAudioBuffer、端のランプ6ms、既定−30dBFS、上限−12dBFS |

長さ情報は254バイトまでは1バイトです。255・256バイトでは`FF`に続けて2バイトの長さを上位側から送り、それぞれ`FF 00 FF`・`FF 01 00`とします。CRCには、この長さ情報全体と本文を含めます。旧版との通信は16バイト以内で使い、長文では送受信側とも新版に更新してください。

`HELLO`の本文は`48 45 4C 4C 4F`、長さは`05`、CRCは`B8`です。
`A`（`41`）は可聴モードで1,876Hzと3,098Hzになります。
プリアンブルの後は固定周期でシンボルを読むので、同じバイトが連続しても区切れます。
マーカーはデータ帯より下にあり、スペクトログラムの32本には含めません。

スペクトログラムの濃さは相対的なFFTパワー（−100〜−20dB）です。音圧レベルの測定ではありません。
最後に判定できた2本を枠でも示します。表示は直近12秒で、動きを減らす設定では描画を毎秒4回以下にします。復調の間隔は変えません。
日本語などの複数バイト文字は必要なバイトがそろってから表示します。

CRCは誤りを検出するだけで、訂正しません。終了マーカーとUTF-8の妥当性も確認します。
確信度は正解の確率ではなく、CRCの一致も完全性や本人の証明にはなりません。
折り返し時の一致率はUnicodeコードポイントを位置ごとに比較し、長い側の文字数を分母にします。
受けるだけ・WAV・送るだけでは、送信元の正解を持たないため一致率を表示しません。

### OfflineAudioContextで確定した値

ChromiumとFirefoxで44.1/48kHzの72条件を確認しました。
34周波数の出力振幅を独立した正弦・余弦の最小二乗法で測った8条件では、−30dBFSに対する最大誤差は0.000001dB未満でした。
送信44.1/48kHzと受信44.1/48kHzに、両帯域・音の長さ85/192ms・送信回数2種類を組み合わせた64条件では、ネイティブのリサンプリング後の波形を独立FFTで解析し、`HELLO日本語`とCRCを復元しました。
追加した384msも、同じ送受信レート・両帯域・1/2回を組み合わせた32条件で復元を確認しました。
以上の測定により、F0=1,500/16,000Hz、間隔94Hz、共通の85/192/384ms・1/2回を確認しました。これはソフトウェア内の検証で、実機の高域特性や到達距離の測定ではありません。

## ⏱️ 転送速度の限界

既定の「長い192ms・全文2回」で比較します。周波数帯と速度の設定を分離しています。

| 項目 | 可聴 | 本気（近超音波） |
|---|---:|---:|
| F0 | 1,500Hz | 16,000Hz |
| データ帯 | 1,500〜4,414Hz | 16,000〜18,914Hz |
| シンボル長 | 192ms | 192ms |
| 全文の送信回数 | 2回 | 2回 |
| 反復込み・付帯情報なし | 2.60B/s | 2.60B/s |
| 256バイトの送信時間 | 102.894s | 102.894s |
| 256バイトの正味速度 | 2.49B/s | 2.49B/s |

| 共通設定 | 反復込み・付帯情報なし | 256バイトの送信時間 | 256バイトの正味速度 |
|---|---:|---:|---:|
| 短い85ms・1回 | 11.76B/s | 23.110s | 11.08B/s |
| 短い85ms・2回 | 5.88B/s | 45.970s | 5.57B/s |
| 長い192ms・1回 | 5.21B/s | 51.572s | 4.96B/s |
| 長い192ms・2回（既定） | 2.60B/s | 102.894s | 2.49B/s |
| もっと長い384ms・1回 | 2.60B/s | 102.644s | 2.49B/s |
| もっと長い384ms・2回 | 1.30B/s | 205.038s | 1.25B/s |

Bはバイトです。反復込み・付帯情報なしの速度は`1 / (シンボル長 × 送信回数)`です。
本文のバイト数をL、付帯情報のシンボル数をH、シンボル長をT、送信回数をRとすると、送信波形の時間は`0.5 + (L + H) × T × R + 0.25 × (R − 1)`秒です。HはLが254以下なら8、255・256なら10です。
前後の無音各250msと反復間隔250msを含みます。許可待ち、自己点検、OS・機材の遅延は含みません。
「約2.5B/s」「約12B/s」をフレーム全体の実効速度と解釈すると過大になります。

本実装では、2048点の解析窓（48kHzで約42.7ms）をシンボルの安定区間に収め、94Hz間隔の候補を分けるために時間を使います。
短くすると反響や処理の遅れの影響が大きくなり、間隔を広げると必要な帯域が増えます。
暗騒音、高域の減衰、マイクの加工、端末差は受信の余裕を減らします。周波数を高くするだけで速くなるわけではありません。

[ggwaveの作者の説明](https://github.com/ggerganov/ggwave#details)では8〜16B/sです。
ggwaveは6本同時・3バイトとReed–Solomon誤り訂正を使います。本ツールは2本同時・1バイトとCRCのみで、通信互換性はありません。
ggwave/quietのコンパイル済み処理を組み込まず、通常スクリプトだけで制限の厳しいCSPと`file://`に対応しています。

## 🔊 環境ノイズと受信への影響

ノイズの影響は、人に聞こえるかどうかだけでは決まりません。
マイクに入った信号のうち、通信に使う周波数と時間に重なる成分が、2本のトーンや開始合図の判定を妨げます。
本ツールのデータ帯は可聴で1,500〜4,414Hz、近超音波で16,000〜18,914Hzです。
開始と終了のマーカーは、それぞれ1,312/1,406Hz、15,812/15,906Hzにあります。
本文の帯域が静かでも、マーカーが妨げられると受信を開始できない場合があります。

「聞こえないノイズ」はホワイトノイズと同じ意味ではありません。
**ホワイトノイズ**は、一定幅の周波数帯ごとのパワーが等しいというスペクトルの性質を表します。実機では扱う帯域が有限で、可聴帯に十分な成分があれば「サー」という音として聞こえます。
低周波音は音の低さを表す分類で、環境省の説明ではおおむね1〜100Hz、そのうち1〜20Hzが超低周波音です。
小さくて聞こえない音、高すぎて聞こえにくい音、入力回路の電気的な雑音も区別します。
定義の参考は[NIのノイズ解説](https://download.ni.com/support/manuals/370192c.pdf)と[環境省「低周波音とは」](https://www.env.go.jp/content/900405790.pdf)です。

以下は、音の性質と本ツールの判定方式から考えられる影響です。各音源を個別に測定した結果や、機種別の成功率ではありません。
同じ機器でも動作状態、距離、配置、入力ゲインによって変わります。

| 音源の例 | 区別したい性質 | 可聴モードへの影響 | 近超音波モードへの影響 |
|---|---|---|---|
| 周辺機器、電源、ディスプレイなどの高い音 | コイル鳴きなどの特定周波数の音。ホワイトノイズとは限らない | 通信帯に重なる成分があると、特定のトーン候補の判定を妨げる | 16〜19kHz付近に成分があれば、人に聞こえにくくても影響し得る |
| スピーカーの「サー」という音、マイクや入力回路の雑音 | 広帯域の音響雑音と、空気を経由しない入力回路の雑音 | 通信帯の雑音が増えると、候補間のパワー差が小さくなる | 実際に高域まで成分がある場合は同様。可聴の「サー」だけで高域の量は判断できない |
| 冷蔵庫、室外機、換気設備の低いうなり | 圧縮機やファンの低域成分、振動、高調波 | 純粋な低周波成分は通信帯から離れる。高調波やがたつき音が帯域に入れば影響する | 純粋な低周波成分の直接の重なりは小さい。強い入力による飽和や機器の加工は別問題 |
| エアコン、扇風機の風切り音 | 連続した広帯域成分。マイクへの直風も含む | 通信帯に重なる風切り音が、送信中ずっと判定の余裕を減らす場合がある | 高域成分とマイクへの直風の強さによる。低域中心でも影響ゼロとは扱わない |
| キーボードのタイピング音 | 短い衝撃音、机から伝わる振動、連続打鍵 | 重なった時刻の本文やマーカーを読み損なう場合がある | 高域まで成分が届く打鍵音なら影響し得る。可聴モードより常に有利とは限らない |
| マウスクリック音 | 短い衝撃音。マイクとの距離が近い場合がある | 1回のクリックでも判定区間に重なると欠落や誤読の原因になる | クリックの高域成分と距離による。短いから無視できるとは限らない |
| 動画、音楽、通知音の再生 | 音声、効果音、音楽などの混合。同じ出力機器では波形も重なる | 通信帯に重なりやすく、再生中の区間で判定を妨げ得る | 音源の高域成分や出力のひずみによる。動画だから高域がないとは扱わない |
| 家庭内の会話、食器、ドア、水音など | 継続音と突発音が混在 | 会話や生活音の帯域と重なる場合や、突発音が判定時刻に重なる場合に影響する | 会話の低域成分だけなら直接の重なりは小さい。食器音などの高域成分は別に確認する |
| 外の車のエンジン音、走行音 | エンジンの低域成分に、タイヤ音などが重なる | 窓や距離による減衰後に残る通信帯の成分が問題になる | 低いうなりだけなら直接の重なりは小さい。広帯域成分や大きな入力の影響は残る |
| インターフォン、ベル、アラーム | 持続する音程、高調波、急な立ち上がり | 特定トーンやマーカーと重なると、その間の複数バイトを読み損なう場合がある | 基音が低くても、高調波や立ち上がりの成分が帯域に入る場合は影響し得る |

低周波音の発生源の例は[環境省の資料](https://www.env.go.jp/content/900405791.pdf)にもありますが、機器の名前だけで周波数成分を決めることはできません。
通信帯の外の音でも、マイクや入力回路が飽和したり、自動ゲインやノイズ抑制が動作したりすると、通信音の振幅や形が変わる場合があります。
本ツールはこれらの加工をオフで要求し、報告された実設定を表示しますが、機器内部のすべての処理を制御できるわけではありません。

比較するときは、機器、配置、送信文、出力レベルを固定し、まず静かな状態、次に1種類の生活音がある状態で受信状況を確認します。
開始合図、長さ情報、本文の読取数、CRCのどこで失敗したかを比べます。
表示グラフはデータ帯の拡大図なので、低周波音や帯域外のマーカーが描かれないことを「存在しない」と解釈しないでください。
1kHzの自己点検が通っても、通信帯すべての到達や耐雑音性を確認したことにはなりません。

### 短い音と長い音の違い

ノイズで「文字がカットされる」と見える場合でも、音そのものが削除されたとは限りません。
トーンが雑音に埋もれる、別の候補を強く拾う、同期が外れる、といった理由でバイトを決められない場合と、誤ったバイトを選ぶ場合があります。
UTF-8の日本語や絵文字は複数バイトでできているため、1バイトの欠落でも1文字を表示できなくなります。

85msの短い音では、2048点の解析窓（48kHzで約42.7ms）が1シンボルに占める割合が大きくなります。
同じ長さのクリック音や反響が重なった場合、判定に使える安定区間を失いやすいと考えられます。
192msや384msでは中央付近の複数のFFT観測を平均する時間に余裕ができますが、FFT自体の周波数分解能は変わりません。
継続的な帯域内雑音、高域の減衰、飽和は、音を長くするだけでは解消しません。送信全体も長くなるため、別の生活音が途中で発生する機会は増えます。

## 🧩 部分受信から誤り訂正へ

### 全文一致と意味の理解

「音が届いた」「一部のバイトを読めた」「全文の検証に合格した」「人が意味を理解できた」は、それぞれ異なる結果です。
たとえば説明用の受信例`MEET AT THE STA?ION`なら、前後の文字と語彙から`STATION`を候補にできます。
一部が欠けても用件が伝わることはあり、文法、定型文、前後の文脈という言語の冗長性が助けになります。
これは[シャノンの論文](https://people.math.harvard.edu/~ctm/home/text/others/shannon/entropy/entropy.pdf)で扱われる、言語の冗長性と雑音下の通信にもつながります。

ただし、`MEET AT 1?`の時刻や、否定語、金額、固有名詞の欠落は意味を変えます。
自然に読める候補が元の文と一致するとは限りません。圧縮データや暗号文などは、人が文脈から補う方法にも頼れません。
**本ツールは文法や意味による候補復元を実装していません。**「?」を自動で埋めたり、推測した文字を検証済みとして表示したりしません。
全文の受信成功は、1つのフレームの本文、CRC、終了マーカー、UTF-8がそろって検証を通った場合です。CRC-8には見逃す誤りもあるため、数学的な無誤りの証明や送信者認証ではありません。

### 全文を2回送る効果と限界

2回送ると、一方にだけ突発音が重なった場合に、もう一方を全文として受信できる可能性があります。
本ツールは各回を独立したフレームとして検証し、正常なフレームが得られた場合はその結果を採用します。
2回の欠けた部分を自動で合成したり、バイトごとの多数決を取ったり、再送を要求したりする機能はありません。
2つの値が食い違うだけでは、単純な多数決でも正しい側を選べません。

仮に各回の全文成功率が同じ`p`で、失敗が互いに独立なら、2回のうち少なくとも1回成功する確率は`1 − (1 − p)²`です。
これは効果を説明するためのモデルで、本ツールの実測成功率ではありません。
継続的な雑音や特定周波数の減衰では同じ位置が両方で欠けやすく、独立という仮定は成り立ちません。
反復は送信時間も増やします。1文字も取得できていない状態から、回数だけを根拠に文字を補うことはできません。

### 電信の課題と将来の拡張

雑音の中で信号と区切りを読み取り、不確かな箇所を送り直してもらう課題は、モールス電信にもあります。
[ITUの国際モールス符号](https://www.itu.int/rec/R-REC-M.1677-1-200910-I)には誤りや反復要求の信号も定められています。
本ツールの2回送信は送信側があらかじめ決めた反復で、受信側からの要求に応じる再送とは異なります。
また、モールス符号そのものや、人が文脈から補う行為を、そのまま誤り訂正符号と呼ぶことはできません。

**誤り訂正符号**は、元のデータに規則的な冗長情報を加え、決められた範囲の誤りや欠落から元のデータを求める方式です。
将来、誤り訂正を追加すれば、一部のバイトが読めない条件でも改善が期待できます。
以下は未実装の設計候補であり、今回追加した機能ではありません。

| 拡張候補 | 期待できる改善 | 必要な条件や代償 |
|---|---|---|
| 短いブロックへの分割と番号付け | 256バイト全体ではなく、失敗した範囲を分けて扱う | メッセージ識別、順序、長さ、各ブロックの検証が必要。付帯情報が増える |
| Reed–Solomonなどの誤り訂正 | 訂正能力の範囲で、誤ったバイトや位置のわかる欠落を復元する | 訂正用の情報と処理が増える。本文だけでなく長さ情報の保護も必要 |
| インターリーブ（並べ替え） | 連続した雑音による損傷を複数の訂正ブロックへ分散する | 単独では訂正しない。誤り訂正との組み合わせ、待ち時間、バッファーが必要 |
| 複数回の受信候補の利用 | 別の回で読めた位置を利用できる可能性 | 同じメッセージの同じ位置であること、矛盾した値の処理、全体の再検証が必要 |
| 受信確認と必要部分の再送 | 失敗したブロックだけを送り直す | 双方向の通信と追加の時間が必要。確認応答自体も失われ得る |
| 言語による候補表示 | 人が用件を推測する補助 | 元のバイト列の保証には使わず、受信値と推測値を明確に分ける |

[ggwave](https://github.com/ggerganov/ggwave#technical-details)は音響通信でReed–Solomonを使う実装例です。
本ツールに追加する場合も、訂正後のデータを再検証し、訂正不能と判定した場合は失敗を示す必要があります。
開始合図を取得できない場合や、通信帯全体が届かない場合まで、本文用の誤り訂正だけで解決できるわけではありません。

## 📡 音響によるエアギャップ通信の可能性

ネットワークを切り離しても、送信側のスピーカーと受信側のマイクを結ぶ音の経路が残れば、データを渡せる可能性があります。
本ツールはその経路を明示的に使う教材で、ページの事前配置、送信側の操作、受信側のマイク許可と動作、共通の方式、音が届く条件が必要です。
隔離した端末へのソフトウェア導入や、権限の取得を実行するものではありません。
独立した研究例として、[HanspachとGoetzの音響通信の論文](https://arxiv.org/abs/1406.1213)がありますが、別方式の実験結果を本ツールの距離や成功率には転用できません。

### 本ツールで確認した範囲

2026-10-21の追加点検では、日本語や絵文字を含む256バイトを、FOSTEX PC200USB-HRからHyperX SoloCastへ物理的に折り返しました。
ブラウザーはChromium、出力は−30dBFS、全文2回です。これは1組の機器と配置での試行で、Vivaldiや2台間通信の測定ではありません。

| 条件 | 観測した結果 |
|---|---|
| 可聴、192ms、256バイト | 1フレームで162バイトを読み取り、94バイトが欠落。全文検証は不合格 |
| 近超音波、192ms、256バイト | 開始合図は認識したが、長さ情報を読めず本文に進めなかった |
| 可聴、384ms、256バイト | 約205秒の送信を完走したが、長さ情報を読めず全文復元に失敗 |
| 対照の`HELLO`、可聴、192ms | この試行では開始合図を認識できず、復元に失敗 |

同じ追加点検のソフトウェア検証では、異なるサンプルレートと両帯域、3種類の音の長さ、1/2回を組み合わせた24条件で256バイトの完全一致を確認しました。
実機の失敗原因は特定しておらず、上の生活音のどれかが原因だったという結果ではありません。
256バイトを扱う実装の確認と、空気を通して安定して届くことの確認は分けて評価します。

### 全文が届かなくても残る情報

全文の検証に失敗しても、正しく読めた断片に用件や識別情報が含まれる場合は、情報の一部が伝わり得ます。
自然言語では前後の文脈から意味を推測できる場合もあり、「CRC不合格だから情報は何も伝わらない」とは評価できません。
一方で、未検証の断片には誤読も含まれ得るため、意味が通じたことを全文の正確な復元と同一視しないことが必要です。
今回の162バイトという数も、任意の文章の意味が伝わることや、安定した漏えい経路を実証した値ではありません。

近超音波は人に気付かれにくい場合がありますが、無音、秘匿、耐雑音性を保証する性質ではありません。
可聴帯の生活音との直接の重なりを減らせても、機器の高域特性や別の高周波音が制約になります。
誤り訂正を導入すれば到達した信号の利用範囲は広げられますが、訂正用の情報によって正味速度は下がり、音の経路自体の不足は残ります。

隔離環境の防御を考える場合は、不要な音声入出力の無効化、マイク権限、近くに置く受信可能な機器、音の通り道を確認する対象になります。
日常の雑音や今回の受信失敗を、そのまま通信を防ぐ対策として頼ることはできません。
本ツールから評価できるのは、選んだ条件で信号や文字がどこまで届くかと、その限界です。

以下の距離は実験室条件（直視、特定機材、最良条件など）の報告値です。最大速度と最大距離を同時に達成したという意味ではありません。
対策欄は経路を減らす考え方の要約で、単独の対策による保証ではありません。

| 経路・手法 | 帯域・受信機 | 距離・条件 | 対策の例 | 出典 |
|---|---|---|---|---|

リンク先のarXivは著者公開版です。arXiv掲載だけを査読済みの根拠にはしていません。
ODINIの数値は引用経由であり、原論文の直接確認と区別します。
音響の方式同士にも差があるため、ggwaveの距離の紹介や他研究の最大距離を本ツールの到達距離として使っていません。
Arpらの2017年の超音波ビーコン研究についても、距離を確認できていない「約2m」という値は採用していません。

## 🔒 プライバシーと安全

- 音声の録音、送受信内容の保存、ネットワーク経由の送信は行わない。言語と明暗だけをlocalStorageへ保存
- 「送るだけ」ではマイクを開かない。受信は最長300秒（5分）。送信は有限長の波形で自動停止
- 停止、タブの非表示、ページを離れる操作、ヘルプ表示、入力のミュート・終了、音声処理の中断で停止
- ミュートが解除されても自動再開しない。開始ボタンからやり直す
- 外部スクリプト・フォント・CDNなし。入力文字はtextContentで表示
- 出力上限−12dBFSはデジタル振幅の上限であり、実際の音圧の上限ではない

GitHub Pagesでは任意のHTTPレスポンスヘッダーを設定できません。指定のmeta CSPは適用しますが、X-Frame-Optionsによる他サイトへの埋め込み防止は提供していません。

OSの音量を小さくして始め、周囲の人やペットに配慮してください。不快ならすぐ止めてください。
人に音を浴びせるための道具ではなく、医療機器でもありません。
作者IPUSIRONはセキュリティ分野の技術書の著者であり、悪用を勧めません。参加者が理解・同意できる環境で使ってください。

## 💻 動作環境と確認範囲

Chromium・Firefoxの実時間音声処理と、Chromium・Firefox・Windows WebKitのWAV復元・表示を自動確認しています。
HTTPと`file://`、幅320・390・1280px、日英、明暗、ヘルプのフォーカス復帰を確認対象にしています。
Windows WebKitの検査用ポートには音声APIがなく、Safari実機の検証の代わりにはなりません。

2台の実機、部屋の反響、機種ごとの高域特性、Bluetooth経路、iPhone/Mac Safari、実際の音量・到達距離は未検証です。
AudioSession APIがある端末では、マイク利用時に`play-and-record`、送信時に`playback`を要求します。
各トーンの最高周波数が解析レートの0.45倍を超える場合や、解析窓が収まらない場合は、そのモードを停止します。
各端末の物理周波数は固定し、FFTビンだけを実際の解析レートから求めます。
